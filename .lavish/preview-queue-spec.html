Preview Processing Queue & Requeue

Make backend preview generation a first-class, observable, re-runnable unit of work — delivering a live processing queue (mirroring the import queue) and a Requeue action at both asset and file level.

The problem

Today, backend preview derivatives are generated inside the import job as an invisible inline sub-stage — not as their own tracked work. Three consequences, all from one root cause:

No status

asset_files carries only preview_object_key (set on success). So pending processing failed unsupported are all indistinguishable from "key is empty". Failures are silent slog.Warns.

No queue

The import queue (/api/imports/events → QueuePage) shows uploads. There is no equivalent surface for previewing — once an import is done, previewing already ran and is unobservable.

No requeue

A bad or missing preview can't be regenerated. There's no endpoint and no UI — the only path is re-importing the whole asset.

Coupled to import

generatePreviews() runs synchronously in pipeline.Run() between thumbnailing and done, so the import blocks on slow renders and previews can't run independently.

Both asks need the same foundation: preview state becomes first-class (a per-file status, aggregatable per asset) and decoupled from the import job so it can be watched and re-run on its own.

Recommended approach — status column + sibling preview pool

The durable state lives on one new column; the orchestration mirrors the proven import machinery without entangling it. No new job table — the per-file status column is the queue.

Why not the alternatives

Option A

Status column + sibling pool

Recommended
  • One new column — minimal schema
  • Reuses proven import pool / broadcaster shape without coupling to it
  • Per-file granularity for the file-level UI comes for free
  • Import pipeline gets simpler than today (no inline render)
  • Queue "rows" are derived via aggregation, not first-class rows
  • A little more query logic for the rollup
Delivers both asks with the least schema and clean reuse. ✓ chosen
Option B

First-class preview_jobs table

  • Closest 1:1 mirror of asset_imports (stable job id, trivial snapshot/resume, run history)
  • You still need per-file status for the file UI — so you maintain both a table and the columns
  • A second state machine to keep in sync with per-file results
  • Over-built: regeneration is already cheap & idempotent (content-addressed)
More machinery than the problem needs.
Option C

Keep inline + status only

  • Least new infrastructure, fastest to build
  • No real processing queue mirroring imports — the headline ask
  • Requeue contends with import worker semantics
  • No independent live progress; file-level requeue is awkward
Fails the explicit "see the processing queue" requirement.
