Manual orphan storage cleanup

A sysadmin-triggered sweep that finds objects in the store no longer referenced by the database, shows them (with any metadata) for review, and deletes only what's confirmed. Deliberately manual for v1 — automation comes later, once we trust it.

branch: feat/large-uploads-storage backend + frontend sysadmin-only builds on the storage overhaul

The problem & the gap

Deleting an asset removes its DB rows but never touches the store — deleteAsset at assets_crud.go:350 comments "Blob storage is untouched — content-addressed, GC is a later job." Failed imports, replaced thumbnails, and purge misfires leave the same dangling objects. Nothing reclaims them today.

The storage interface can't even see what's there: it has DeleteOriginal but no List, no DeleteBlob, no DeleteThumb. The metadata we just added (storage.go:17) was designed "as a fallback for DB-loss recovery and orphan sweeps" — this is the sweep it anticipated.

What counts as an orphan

An object is orphaned when its content-hash key is referenced by no live DB row. Because storage is content-addressed and deduped, "referenced" means the union across every column that can point at a key:

PrefixLive references (the "known set")
blobs/asset_files.object_key
thumbs/assets.thumbnail_object_key  ∪  asset_files.preview_object_key
originals/asset_versions.original_package_object_key  WHERE purged = false

Purged originals (original_package_purged = true) are excluded from the known set on purpose: the DB already says that object should be gone, so a leftover from a failed purge becomes a legitimate cleanup target. If the same content hash is still referenced by a non-purged version, the union keeps it safe.

The flow

1 · SCAN
List all three prefixes, diff against the known set, apply the age filter → candidate list
→
2 · REVIEW
Sysadmin sees each candidate: prefix, key, size, age, and metadata (filename / IDs) if present
→
3 · DELETE
Confirm selection → re-verify each is still orphaned + old enough → delete → audit-log each
The one dangerous failure mode: deleting in-flight uploads.

Objects are written to the store before their DB rows commit (the whole D1 upload-ordering from the last spec; extraction also writes blobs before asset_files exist). A scan running mid-import would see freshly-written, not-yet-referenced objects and flag them as orphans. Two independent guards stop this:

  • Minimum-age filter — objects newer than a threshold (default 7 days) are never candidates. Covers the entire write→commit window with enormous margin.
  • Re-verify at delete time — between scan and confirm, dedup means a brand-new upload could reference an "orphan" hash. Each key is re-checked (not-referenced + old-enough + still-exists) immediately before Delete; anything that changed is skipped with a reason.

Chosen approach

A pair of sysadmin-only endpoints reusing the existing admin surface (requireSysadmin, routes at handler.go:126), a small orphan-detection service that generalises the reference-count logic already in maybePurgeOriginal (pipeline.go:223), and a review panel in the existing ServerAdminSection. Deletions are audited server-level via the existing audit.Write.

New storage primitives

List(ctx, prefix) → keys + size + last-modified (cheap, one paginated ListObjectsV2).
StatMeta(ctx, prefix, key) → HEAD/sidecar → ObjectMeta (only for candidates).
Delete(ctx, prefix, key) → generic delete; DeleteOriginal becomes a thin wrapper.

Cost shape

List is one paginated call per prefix. Metadata needs a HEAD per object — so we fetch it only for the orphan candidates, not the whole bucket. Thumbs carry no metadata (written via PutThumb), so their rows just show none.

Scope boundaries

In scope

Manual scan + review + delete over blobs/thumbs/originals; new List/Delete/StatMeta primitives; sysadmin UI; per-deletion audit.

Out of scope (later)

Automatic/scheduled sweeps (the audit.Purger ticker is the template when we're confident); DB-side GC of soft-deleted rows; reconciling missing objects (DB row → no object).
