File Preview — Spec Alignment

Inline previews for the scoped file browser, across every file type Damson stores. This surface is for aligning on scope, architecture, and staging before the spec is written — annotate anything, and answer the decisions near the bottom.

Goal & current state

What exists today

The file browser (FileBrowser.tsx) opens a detail panel per file. It shows a backend thumbnail and, for png/jpg/gif/webp only, an inline full image fetched as an auth blob (useFileObjectUrl.ts). Everything else gets a type icon.

Backend already renders thumbnails (raster / audio waveform / font specimen) in pure Go via the import pipeline.

What we want

A real preview per file type in the detail panel — larger, richer, sometimes interactive (zoom, scrub, 3D orbit, syntax highlight, page through a PDF) — using the safest feasible path for each type.

The two corrections that shape this whole plan.

① No CSP exists. Our only policy is nosniff + attachment disposition. Several previews put untrusted-derived content near the DOM (Markdown, docx, SVG, PDF), so introducing a Content-Security-Policy is a prerequisite, not something we already have.

② Derivatives are per-asset today, but previews are per-file. ThumbnailObjectKey lives on Asset; AssetFile has no derivative slot. So backend previews need a new per-file column (migration parity: SQL + GORM) and a new pipeline traversal over each file — not a tweak to the existing single-thumbnail step.

Proposed architecture

Two delivery models — chosen per file type

LIVE CLIENT RENDER

Fetch the file as an authenticated blob → hand the Blob/ArrayBuffer straight to a lazy-loaded viewer in the browser. No backend, no derivative, no worker. For everything cheap & safe: text, code, native images/audio, fonts, JSON/CSV, web-native 3D.

DERIVATIVE AT IMPORT

The import worker pre-renders a small, safe, web-friendly artifact once (flattened PNG, PDF poster, GLB). The panel just fetches that. For expensive or browser-unopenable types: pro/HDR images, PDF, SVG raster, FBX.

Backend: one new pipeline stage

The import pipeline is a clean state machine, idempotent & resume-on-startup. We add StagePreviewing after thumbnailing — it iterates the version's AssetFile rows and generates a per-file derivative for eligible types, content-addressed into the existing thumb namespace.

Frontend: a FilePreview dispatcher

A single component keyed by file type that lazy-import()s the right viewer (so three.js/pdf.js/Shiki never touch the main bundle), driven by the same auth-blob hook generalized from useFileObjectUrl. Falls back to the current thumbnail/icon when no viewer applies or a derivative is missing.

Proposed staging

Each stage is independently committable and shippable. Ordered so the free client-only wins land first and the backend foundation can follow. You asked to settle staging here — Decision D5 below lets you reshape it.

  1. FoundationCSP · dispatcher · blob hook
    Introduce a Content-Security-Policy middleware. Generalize the auth-blob hook. Scaffold the FilePreview dispatcher with icon/thumbnail fallback. Unblocks every DOM-touching preview.
  2. Text-family previewsclient-only
    Shiki for code + shaders + txt; react-markdown + sanitize for md; JSON/XML/CSV viewers (virtualised, size-capped); Unity-YAML tree. High coverage, zero backend/deploy risk.
  3. Media previewsclient-only
    Native-image zoom + checkerboard; native-codec audio via <audio>+wavesurfer; font specimen via @font-face; safe zip directory listing; hex/metadata for dll/bytes.
  4. Per-file derivative foundationbackend · migration
    New AssetFile preview columns (SQL + GORM parity), StagePreviewing stage, generator extension, per-library toggle, preview-serving endpoint, resume coverage. No new file type yet — wires the rails.
  5. Pro/HDR image derivativesbackend · pure-Go
    PSD/EXR/TGA/TIFF/BMP → flattened PNG/JPEG via pure-Go decoders. The biggest backend payoff for the least cost.
  6. SVG safe previewper D2
    Backend raster (oksvg) or client sanitize-and-<img>, with download-only fallback.
  7. PDFclient + WASM
    pdf.js client viewer (isEvalSupported:false, enableScripting:false, same-origin worker) + backend first-page poster via WASM-PDFium (klippa-app/go-pdfium, wazero — stays CGo-free). Gated by Decision D3.
  8. 3D meshesoptional
    three.js viewer for obj/dae/glb; FBX best-effort client + optional opt-in FBX→GLB stage. Gated by Decision D4.

D2 SVG previews

SVG carries active content; it's deliberately excluded from inline preview today.

D3 PDF preview depth

PDF is the one document type with real demand. The backend poster embeds a multi-MB PDFium-WASM blob (go:embed, ~2× slower than native but CGo-free).

D4 3D mesh scope

obj/dae/glb work live in three.js. FBX is the hard case (closed format; reliable preview needs a native FBX→GLB conversion + subprocess sandbox).
