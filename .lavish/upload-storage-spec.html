Large Uploads & Storage Overhaul

Fix the >500 MB upload failures on the S3/Garage backend, and land three storage improvements that share the same code: object metadata (a DB-loss fallback), an originals/ prefix, and enforcing RetainOriginalPackages. This surface is for aligning on scope & design before the spec is written — annotate anything, answer the decisions near the bottom.

design-only → spec no code yet validated vs. codebase orphan-GC = out of scope

Why >500 MB uploads fail today

The S3 backend buffers the whole file in RAM.

putHashed does io.ReadAll(r) into a single []byte, then keeps it for the PutObject body — internal/services/storage/s3.go:104,128. A 500 MB upload is 500 MB+ resident, and io.ReadAll's slice-doubling spikes to ~2×. In a memory-capped container that OOMs; "~500 MB" is just where the ceiling sits. There is no multipart/streaming path — the code comment at s3.go:100 says it was deliberately deferred.

Not the cause (ruled out)

MaxUploadBytes (2 GiB, models/settings.go:7) is dead code — editable in admin, never read in the upload path. No MaxBytesReader on the route (jsonBodyCap skips multipart/*, main.go:288). ReadTimeout is 30 min.

LocalFS is already fine

It streams to a temp file through a hash MultiWriter then renames — localfs.go:88. The fix makes S3 behave like LocalFS already does. Check your deploy too: a reverse proxy (nginx client_max_body_size default 1 MB) and a small temp-dir tmpfs can independently cap uploads.

Proposed approach — four threads on the storage layer

All four touch storage.Service and its two implementations, so they ship together. Ordered by dependency below.

THREAD 1  Stream large uploads (constant memory)

Rewrite the S3 putHashed to mirror LocalFS: stream the reader to a temp file through a sha256 MultiWriter (keeps content-addressing), then upload the seekable temp file with the AWS SDK v2 feature/s3/manager Uploader, which chunks into parts automatically. Memory stays flat regardless of size.

Deploy provides a ~20 GB tmpfs for the temp dir (via TMPDIR/os.TempDir()). The io.LimitReader extraction entries (up to 2 GiB each, unitypackage.go:179) go through the same PutBlob and get the fix for free.

THREAD 2  Object metadata — a DB-loss / orphan-sweep fallback

Today PutObject writes only Bucket/Key/Body — no metadata (s3.go:125). All filename info lives only in Postgres (asset_files.relative_path). Attach plaintext original filename + owning IDs to the object so a blob is self-describing if the DB is lost or you're eyeballing a sweep.

Accepted tradeoffs (your call, confirmed).

① Write-once + dedup: identical bytes HEAD-skip the re-upload, so metadata records the first uploader's filename/IDs only. Fine — this is a fallback, not the sweep mechanism. The DB stays source of truth.

② Non-ASCII filenames are URL-encoded (HTTP header values must be ASCII).

THREAD 3  Enforce RetainOriginalPackages

The per-library flag exists (default true) but is never enforced — read/written via API only. When false, purge the original archive after a successful Unity extraction. Needs a new Delete on the storage interface (there is none today — storage.go).

Only true archives (unitypackage; zip later) are purged — a loose upload's "original" is its content blob, so it's never purged. Purge fires only on extraction success, after asset_files commit; on failure the archive is kept for retry/debug. Downstream effects when purged: re-extract (assets.go:442) and download-original (files.go:70) return "no retained package" — the intended meaning of retain=off.

THREAD 4  originals/ prefix

The uploaded archive currently lands in the shared blobs/ pool via PutBlob (assets.go:311). Give true archives their own originals/ prefix, so retain/purge and future sweeps operate on it independently of extracted-content blobs.

loose upload
blobs/ — content & "original" are the same object (unchanged)
.unitypackage
originals/ — the archive; extracted files still go to blobs/
thumbs
thumbs/ — unchanged

Blast radius: retrieval of the original must know the prefix. Six call sites read OriginalPackageObjectKey today (pipeline extract + thumbnail, re-extract, reimport, download, resume). They'll route by package_kind (loose→blobs/, archive→originals/) via one small helper. See decision D2.

Bonus — wire up MaxUploadBytes.

Since we're in the upload path anyway, enforce the existing (dead) 2 GiB server setting so oversized uploads are rejected cleanly instead of filling the tmpfs. See decision D4.

D1 How are the owning IDs captured into metadata?

The snag: PutBlob runs before the DB rows exist (upload handler) and extraction stores content before asset_files is written — so IDs aren't known at first write. Content-addressing forces store-then-identify.

Risks & things I'll verify

infra

tmpfs must have room for the largest concurrent uploads (N × filesize). Streaming fixes RAM, not disk. Also confirm no reverse-proxy body cap in front of Damson.

dedup

A blob shared across libraries carries the first uploader's metadata & IDs. Accepted — documented as fallback-only.

migration

Existing Unity originals stay under blobs/. New split applies to new uploads; retrieval branch must tolerate old-key-in-blobs/. I'll HEAD-fallback across both prefixes for originals, or document a one-off migration.

re-extract

If retain=off, re-extract & download-original are unavailable by design. Confirm the UI degrades gracefully (has_original=false already gates it).
