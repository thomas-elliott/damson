# Audit log: paging, labels, retention

Covers DAM-51, DAM-55 and DAM-57

## Why are we doing this

An admin can page through the whole audit log, read every entry in words, and trust that entries
past the retention period are deleted.

## Steering

Task rung, 2026-10-24, operator:

- "DAM-51, page the audit log. /audit and /admin/audit stop at 200 entries. DAM-39 just built
  paging for the library view, so this can reuse that pattern."
- "DAM-57, label every action type. At least six types the backend writes show as raw strings. The
  fix should also make the chip test fail when a type has no label."
- "DAM-55, enforce audit retention. Settings stores a retention period, but nothing deletes old
  entries yet."

## Design

none. Direct decision, reusing the library view's paging from DAM-39.

## Decisions

### How do the audit pages page?
Answer: `/audit` and `/admin/audit` get the library view's pager. Page and page size are kept in
the URL; sizes 25, 50, 100 and 200; default 50. Changing an action chip, the search or the admin
scope goes back to page 1, and a page past the end moves to the last page.
By: recommended, operator said "go with all of them" (2026-10-25)

### What does the "Filter by user" box search?
Answer: it searches on the server, across every entry in the feed, matching user name, user email
and action type as it does today. It no longer filters only the rows already loaded.
By: recommended, operator said "go with all of them" (2026-10-25)

### Do the asset panel and project page activity feeds change?
Answer: no. They keep showing the latest 50 entries.
By: recommended, operator said "go with all of them" (2026-10-25)

### Which action types get a label?
Answer: every type the backend writes. The thirteen without one today are `asset.merge`,
`asset.rescan`, `asset.unreview`, `asset.metadata.apply`, `asset.reference.create`,
`asset.reference.update`, `asset.version.update`, `asset.version.delete`, `token.create`,
`token.revoke`, `library.create`, `library.delete` and `admin.storage.orphan_delete`.
By: recommended, operator said "go with all of them" (2026-10-25)

### How does a missing label get caught?
Answer: the Go audit package holds the one list of action types, and `audit.Write` refuses a type
not on it. A Go test keeps a checked-in copy of that list under `web/src/lib` in step with it. The
Vitest fails when a type on the list has no label, or when a library-feed type has no chip.
By: recommended, operator said "go with all of them" (2026-10-25)

### What does retention need beyond the existing purge job?
Answer: the purge job already deletes each library's entries older than its setting once a day.
The Settings help text changes to say that entries older than the setting are deleted once a day,
and the first sweep runs shortly after the server starts instead of one interval later.
By: recommended, operator said "go with all of them" (2026-10-25)

## Acceptance

- On `/audit`, with more entries than one page, the pager reaches the oldest entry; reload and
  back/forward return to the same page and page size.
- On `/admin/audit`, in both Server and All libraries scopes, the pager reaches the oldest entry.
- Changing a chip, the search or the scope shows page 1; a `?page=` past the end shows the last
  page.
- Searching "Filter by user" for a user whose entries are only on a later page finds them.
- No entry on either audit page shows a raw action type string.
- Every library-feed action type is reachable from a chip other than All.
- Adding an action type to the backend without a label, or a library type without a chip, fails
  `just check`.
- Settings describes retention as deleting entries older than the setting once a day, with no
  "not yet enforced".
- With retention set, entries older than it are gone shortly after a server restart, without
  waiting a day.

## Out of scope

- Paging the activity feeds in the asset panel and on project pages.
- Retention for server-level events (`library_id` NULL); there is no server setting for it.
- Changing the purge interval or its `DAMSON_AUDIT_PURGE_INTERVAL` default.

## Implementation report

Mode: committing, one commit per stage (repo AGENTS.md), on branch `dam-51-55-57-audit-log`.

### Stages

1. Action-type registry and labels (DAM-57): one list of action types in `internal/services/audit`,
   `audit.Write` refuses others, a checked-in copy under `web/src/lib` kept in step by a Go test,
   a label for every type, and a Vitest that fails on a missing label or chip.
2. Server-side audit search (DAM-51): a `q` filter on the audit endpoints matching user name, user
   email and action type.
3. Page `/audit` and `/admin/audit` (DAM-51): the library view's pager, page and size in the URL,
   reset to page 1 on chip, search or scope change, clamp past the end; e2e coverage.
4. Retention (DAM-55): the first purge sweep runs shortly after start; Settings help text.

### Choices made
- `web/src/lib/auditFormat.ts`: `api_token` and `storage_object` targets read "token" and
  "storage object", so the new token and orphan rows show no raw target type either.
- `web/src/lib/auditFilters.test.ts`: also fails on a verb for a type the backend does not write.
- `web/src/components/UrlPager.tsx`: the audit pages share one URL-backed pager (clamp, history
  push, size reset) built on `parsePaging`/`withPage`; `LibraryPage` keeps its own inline copy.
- `web/src/pages/AuditPage.tsx`, `AdminAuditPage.tsx`: the pager sits under the list,
  right-aligned, and hides when the feed is empty.
- `web/src/hooks/useDataQueries.ts`: both paged audit hooks keep the previous page on screen while
  the next loads, as `useAssets` does.
- `internal/services/audit/purge.go`: the first sweep runs as soon as `Run` starts, with no delay.
