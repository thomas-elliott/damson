# Research-agent prompt — File preview feasibility (paste into claude.ai)

> Copy everything below the line into Claude on the web. It is self-contained — it
> embeds the brief, so the agent needs no repo access. Turn on web search / research mode.

---

You are a **technical research agent**. Your job is a **feasibility survey**, not code and
not a final design. I'm building a self-hosted digital-asset manager ("Damson", Go backend
+ React/TypeScript frontend) and need to know, **for each file type it stores, the feasible
ways to render an inline preview** — libraries, specs, WASM modules, native tools — and a
recommendation for each.

A scoping brief follows. It references internal file paths (e.g.
`internal/services/thumbnail`) — **you cannot and need not open these**; they only tell you
what already exists and what the constraints are. Your research target is the **external
ecosystem**: libraries, specs, browser capabilities, and tools that satisfy the brief.

## How to work

- **Use web search.** Verify each library/tool is real and current: check last release date,
  maintenance status (archived? active?), licence, and whether it works in a browser (ESM,
  WASM) or as a Go/native backend dependency. Cite sources (link + date).
- **Respect the hard constraints** in §1 of the brief — they eliminate most generic
  answers (auth-gated blobs, restrictive security policy, pure-Go backend, large files).
  An answer that ignores them (e.g. "just use `<img src=url>`") is wrong here.
- **Evaluate every type against both delivery models:** live client-side render vs.
  derivative generated by the background worker at import (§2). Say which fits and why.
- **Prefer breadth and decisiveness.** A clear verdict per type with 1–2 alternatives beats
  an exhaustive essay on one. Where the honest answer is "download-only, no practical
  preview", say so — that's a valid, useful finding.
- **Don't recommend heavyweight machinery casually.** Native deps (Blender, ffmpeg,
  ImageMagick) and sandboxing (containers, gVisor) each carry a real cost against a pure-Go
  single-binary deployment — only recommend them where genuinely warranted, and say so.

## Output format

1. A short **executive summary**: the 3–5 decisions that matter most, and any type where
   the realistic answer is "not worth it".
2. A **per-type section** (one per group in §3 of the brief) following the **"What to
   produce per file type"** structure in §4 — verdict, recommended approach + alternatives
   (with maintenance/licence/bundle-or-native cost/security notes), client-vs-backend and
   live-vs-derivative timing, large-file handling, and an effort signal.
3. A **cross-cutting notes** section: shared libraries/patterns reusable across types,
   security pitfalls, and anything that changes the build-vs-skip calculus.
4. A **sources** list with links and access dates.

# Embedded brief

## 0. What Damson is

A self-hosted digital-asset manager for game-development assets (heavy on Unity content:
prefabs, meshes, textures, materials, scenes, shaders, animations). Backend is **Go**
(Gin + GORM, single static binary, currently **pure-Go** media decoders, no CGo). Frontend
is **React + TypeScript (strict) + Vite**, TanStack Query v5, Tailwind, Radix primitives.
Files live in pluggable storage (local FS or S3-compatible). A scoped file browser is
shipped, with a **detail panel** that currently previews only a handful of raster image
formats inline; we want to widen what it can preview, per file type.

## 1. Context the research must respect

There are two distinct render surfaces — do not conflate them:

| Surface | Exists today | Where rendered | Scope of this research |
|---|---|---|---|
| **Thumbnail** (≤512px, grid cell) | yes (backend service) | backend → static image | reuse/extend only |
| **Preview** (detail panel, large/interactive) | raster images only | client, object URL | **the target** |

### Hard constraints (these eliminate most generic answers)

1. **Auth-gated blob delivery.** Files are *not* served from public URLs. The client
   fetches the file with a bearer token and builds a `blob:` object URL. Any preview that
   assumes a plain `<img src>` / `<video src>` / CDN URL **will not work** — recommendations
   must work from an authenticated `fetch` → `Blob`/`ArrayBuffer`, or from a backend render.
2. **Security policy is restrictive on purpose.** Responses are served with `nosniff` +
   attachment disposition. SVG is *deliberately excluded* from inline preview (attacker-
   controlled active content). Any format that can carry script, external refs, or
   decompression bombs (SVG, HTML, PDF JS, SVG-in-font, zip) needs an explicit risk note
   plus a sanitisation/sandboxing strategy, or a "render on backend to a safe raster" call.
3. **Two render locations are both on the table — pick per type:** client-side
   (browser-native, JS, or WASM) for text/code, simple images, natively-decoded
   audio/video; **backend pre-render to a safe artifact** for formats browsers can't open
   (PSD, EXR, FBX) or that are unsafe to hand to the browser raw.
4. **Backend is Go, pure-Go decoders today** (`golang.org/x/image`, `go-mp3`, `oggvorbis`,
   `x/image/font`). `libvips` is reportedly in the runtime image but **unused**. For any
   backend-render recommendation, state whether it needs CGo / a native binary (ImageMagick,
   libvips, ffmpeg, Blender headless, Assimp) and weigh it against the pure-Go single-binary
   deployment.
5. **Assets can be large.** FBX meshes, layered PSDs, EXRs can be tens–hundreds of MB. Flag
   where streaming, range requests, downsampling, or "preview a pre-rendered derivative
   instead of the original" is necessary.
6. **Client stack:** React + TS (strict) + Vite, TanStack Query v5, Tailwind, Radix. Prefer
   libraries that are tree-shakeable, ESM, and lazy-loadable (preview code must not bloat
   the main bundle).

## 2. Preview-derivative generation (background worker)

The likely delivery model — and a primary axis to evaluate against — is **generating
preview derivatives asynchronously after import**, not on-demand at view time. For
expensive types (large meshes, layered PSDs, EXRs, PDFs) we'd produce a smaller, web-
friendly, safe-to-serve artifact once (e.g. a downsampled glTF, a flattened PNG, a
normalised JSON, a poster image), then the detail panel just fetches that.

**This infrastructure already exists** — assume we extend it rather than invent it: a
bounded background worker pool drains an import job queue (resumable on startup) and runs a
**staged pipeline** that already generates thumbnails as one stage, gated by **per-library
toggles**. So "preview derivative" generation is naturally one more pipeline stage emitting
one more stored artifact per file, idempotent + resumable, behind a per-type enable toggle.

**Research questions this raises (answer per expensive type):**

1. **Derivative format** — the right web-friendly, safe-to-serve output? (meshes →
   glTF/GLB or rendered poster; PSD/EXR/TGA → flattened PNG/JPEG; PDF → first-page poster +
   lazy pages; large JSON/CSV → truncated/normalised preview.)
2. **Where it runs** — pure-Go in-process (preferred) vs. a native tool the worker shells
   out to (Blender headless, ImageMagick/libvips, ffmpeg, Assimp). State the dependency cost.
3. **Sandboxing — keep it proportional** (a goal is to *avoid* heavy isolation). For each
   type needing an untrusted native parser, give the *minimum* viable containment and
   whether it's warranted at all:
   - in-process pure-Go with resource caps (timeout, max-dimensions, decompression-bomb
     guards) — lightest;
   - subprocess with rlimits / timeout / temp-dir scoping — moderate;
   - container / seccomp / gVisor / WASM sandbox — last resort, only if a format genuinely
     demands running untrusted native code (flag explicitly).
   Note which types need **no** sandbox.
4. **Cost controls** — per-library toggle, size ceilings above which we skip derivative
   generation and fall back to download-only, and graceful failure (icon/metadata fallback).

Where a type is cheap and safe to render live in the browser from the auth blob (text,
code, native images/audio, fonts), the worker path is unnecessary — **say so** so we don't
over-build. Each per-type answer must state **derivative-at-import vs. live-client-render**.

## 3. File types to research

| Group | Extensions | Today | Core research question |
|---|---|---|---|
| **Raster images** | png, jpg/jpeg, gif, webp | inline preview ✓ | Anything beyond native `<img>` needed (zoom/pan, colour profile, alpha checkerboard)? |
| **Pro/HDR images** | tga, psd, exr, tif/tiff, bmp | thumbnail only | Browser can't decode these. Client WASM decoders vs. backend pre-render to PNG. PSD = flatten or show layers? EXR = tone-mapping. |
| **Vector** | svg | excluded (security) | Safe inline render: sanitise (DOMPurify) + `<img>`/inline, or backend rasterise. State residual risk. |
| **3D meshes** | fbx, obj, blend, dae | icon only | Interactive WebGL viewer (three.js + loaders) vs. backend-rendered turntable/still. Which formats have reliable web loaders? `.blend` and `.fbx` are the hard ones. |
| **Unity assets** | prefab, unity (scene), mat, anim, controller | icon only | YAML or binary Unity serialised files referencing GUIDs. Is a *meaningful* preview possible (structured summary, referenced-asset resolution) or is best-effort a formatted text/metadata view? |
| **Code/scripts** | cs, js, ts, py | icon only | Syntax-highlighted text view: which highlighter (Shiki vs. Prism vs. highlight.js), bundle cost, lazy grammar loading. |
| **Shaders** | shader, cginc, hlsl, compute | icon only | Same as code — highlighting + grammar availability for HLSL/ShaderLab. |
| **Audio** | wav, mp3, ogg, aiff, flac | waveform thumbnail ✓ | Inline `<audio>` from blob + waveform/scrub UI (wavesurfer.js?). Which formats decode natively vs. need transcode (aiff, flac). |
| **Fonts** | ttf, otf, woff, woff2 | specimen thumbnail ✓ | Interactive specimen (live `@font-face` from blob, editable sample text). Native browser support per format. |
| **Documents** | pdf, md, txt, rtf, doc, docx | icon only | PDF: pdf.js feasibility under blob+CSP. Markdown: render + sanitise. docx/rtf: client lib (mammoth.js?) vs. backend convert vs. download-only. |
| **Data** | json, xml, csv, asset, bytes, dll, zip | icon only | json/xml/csv: pretty/table view (size limits, virtualisation). `.asset`/`.bytes`/`.dll`/`.zip`: realistically download-only or hex/metadata — confirm. zip = list contents safely (bomb risk). |

## 4. What to produce per file type

For each group (or notable extension within it), return:

1. **Verdict** — one of: native-browser, client-library, client-WASM, backend-pre-render,
   metadata/structured-only, download-only.
2. **Recommended approach** + 1–2 named alternatives, each with: library/spec/WASM name,
   maintenance status, licence, last release; bundle-size or native-dependency cost;
   whether it works from an authenticated `Blob`/`ArrayBuffer` (constraint #1); security
   notes (#2) + required sanitisation/sandboxing.
3. **Render location + timing** — client vs. backend, *and* derivative-at-import (§2) vs.
   live-client-render, with rationale against the pure-Go single-binary deployment (#4).
   If a derivative, name its output format and any native dep + sandboxing need.
4. **Size/perf handling** for large inputs (#5).
5. **Effort signal** — trivial / moderate / heavy / not-worth-it.

Prioritise breadth and feasibility over depth; this feeds a later per-type implementation
decision, not code.
